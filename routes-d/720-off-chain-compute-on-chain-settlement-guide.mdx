# Off-Chain Compute with On-Chain Settlement on Stellar

Soroban contracts execute within tight instruction and memory limits. Many workloads — machine-learning inference, large set reconciliations, complex financial simulations — are prohibitively expensive to run entirely on-chain. The off-chain compute / on-chain settlement pattern decouples the heavy computation from the settlement: work is done off-chain, and only the verified result and its proof are committed to the ledger.

---

## Trust Model

The central question is: how does the on-chain contract know the off-chain result is correct?

### Option 1 — Optimistic (dispute window)

The result is submitted and accepted after a challenge period. Anyone can dispute by re-running the computation and providing a fraud proof. If no dispute arrives within the window, the result is finalised.

**When to use**: computations that are expensive to verify but rare to dispute; settlement amounts large enough to justify watchtower infrastructure.

### Option 2 — Pessimistic (commit-reveal with verifiable result)

The off-chain worker commits a hash of the result first, then reveals the result after the input is locked. The contract verifies the reveal against the commit. No fraud-proof circuit needed, but the contract must be able to re-verify the result itself — feasible for deterministic hashes or signature checks.

**When to use**: short, auditable computations where on-chain re-verification is cheap (e.g. verifying a Merkle proof, checking an ECDSA signature over a result).

### Option 3 — Trusted executor with multi-sig

A committee of known executors each sign the result off-chain. The contract checks N-of-M signatures before accepting. Trust is social, not cryptographic.

**When to use**: internal systems where executor identities are known and bound by legal/operational agreements.

This guide implements **Option 3** (multi-sig committee) because it requires no ZK infrastructure, maps well to Soroban's native auth primitives, and is the most practical starting point for most Stellar teams.

## Settlement Flow

```
┌────────────────────────────────────────────────────────────────┐
│  1. Client submits computation request to off-chain workers    │
│     (REST call, message queue, etc.)                           │
└───────────────────────┬────────────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────────────┐
│  2. Each worker runs the computation independently             │
│     and signs: sha256(job_id || result_bytes)                  │
└───────────────────────┬────────────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────────────┐
│  3. Aggregator collects N-of-M signatures; submits to Soroban  │
│     contract via settle(job_id, result, sigs[])                │
└───────────────────────┬────────────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────────────┐
│  4. Contract verifies signatures, stores result, emits event   │
│     Consumer reads result from contract storage or event log   │
└────────────────────────────────────────────────────────────────┘
```

## Reference Implementation

### Soroban Settlement Contract

```rust
// contracts/settlement/src/lib.rs
#![no_std]
use soroban_sdk::{
    contract, contractimpl, contracttype, crypto::Hash,
    vec, Address, BytesN, Env, Vec,
};

#[contracttype]
pub struct JobResult {
    pub result: BytesN<32>, // sha256 of the result payload
    pub settled_at: u64,
}

const EXECUTORS_KEY: &str = "executors";
const THRESHOLD_KEY: &str = "threshold";

#[contract]
pub struct SettlementContract;

#[contractimpl]
impl SettlementContract {
    /// One-time setup: register the trusted executor committee.
    pub fn initialize(env: Env, executors: Vec<Address>, threshold: u32) {
        assert!(threshold as usize <= executors.len(), "threshold > committee size");
        env.storage().instance().set(&EXECUTORS_KEY, &executors);
        env.storage().instance().set(&THRESHOLD_KEY, &threshold);
    }

    /// Submit a settled result. `result_hash` is sha256(job_id || payload).
    /// Each executor in `signers` must have called require_auth before this.
    pub fn settle(
        env: Env,
        job_id: BytesN<32>,
        result_hash: BytesN<32>,
        signers: Vec<Address>,
    ) {
        let executors: Vec<Address> = env
            .storage()
            .instance()
            .get(&EXECUTORS_KEY)
            .unwrap();
        let threshold: u32 = env
            .storage()
            .instance()
            .get(&THRESHOLD_KEY)
            .unwrap();

        // Verify each signer is an authorised executor
        let mut valid: u32 = 0;
        for signer in signers.iter() {
            signer.require_auth();
            if executors.contains(&signer) {
                valid += 1;
            }
        }
        assert!(valid >= threshold, "insufficient executor signatures");

        // Reject replays
        assert!(
            !env.storage().persistent().has(&job_id),
            "job already settled"
        );

        env.storage().persistent().set(
            &job_id,
            &JobResult {
                result: result_hash,
                settled_at: env.ledger().timestamp(),
            },
        );

        env.events().publish(
            (job_id.clone(),),
            result_hash.clone(),
        );
    }

    pub fn get_result(env: Env, job_id: BytesN<32>) -> Option<JobResult> {
        env.storage().persistent().get(&job_id)
    }
}
```

### Off-Chain Worker (TypeScript)

```ts
// workers/compute-worker.ts
import { createHash } from 'crypto';
import { Keypair, hash } from '@stellar/stellar-sdk';

export interface Job {
  id: Buffer; // 32 bytes
  input: unknown;
}

export interface SignedResult {
  jobId: Buffer;
  resultHash: Buffer;
  signature: Buffer;
  publicKey: string;
}

/** Run the computation and sign the result. */
export async function computeAndSign(
  job: Job,
  executorKeypair: Keypair,
): Promise<SignedResult> {
  // Replace with your actual computation
  const result = await runComputation(job.input);
  const payload = Buffer.from(JSON.stringify(result));

  // result_hash = sha256(job_id || payload)
  const preimage = Buffer.concat([job.id, payload]);
  const resultHash = createHash('sha256').update(preimage).digest();

  const signature = executorKeypair.sign(resultHash);
  return {
    jobId: job.id,
    resultHash,
    signature,
    publicKey: executorKeypair.publicKey(),
  };
}

async function runComputation(input: unknown): Promise<unknown> {
  // Your expensive off-chain logic here
  return input;
}
```

### Aggregator (TypeScript)

```ts
// workers/aggregator.ts
import {
  Contract,
  Networks,
  TransactionBuilder,
  BASE_FEE,
  rpc,
  Address,
  nativeToScVal,
  xdr,
} from '@stellar/stellar-sdk';
import type { SignedResult } from './compute-worker';

const RPC_URL = process.env.RPC_URL!;
const CONTRACT_ID = process.env.SETTLEMENT_CONTRACT!;

export async function submitSettlement(
  aggregatorKeypair: { publicKey(): string; sign(tx: any): void },
  results: SignedResult[],
  threshold: number,
): Promise<void> {
  if (results.length < threshold) throw new Error('Not enough signatures');

  // All results must agree on the same hash
  const hashes = new Set(results.map(r => r.resultHash.toString('hex')));
  if (hashes.size !== 1) throw new Error('Executor disagreement');

  const jobId = results[0].jobId;
  const resultHash = results[0].resultHash;

  const server = new rpc.Server(RPC_URL);
  const account = await server.getAccount(aggregatorKeypair.publicKey());
  const contract = new Contract(CONTRACT_ID);

  const signers = results
    .slice(0, threshold)
    .map(r => new Address(r.publicKey).toScVal());

  const tx = new TransactionBuilder(account, {
    fee: BASE_FEE,
    networkPassphrase: Networks.TESTNET,
  })
    .addOperation(
      contract.call(
        'settle',
        nativeToScVal(jobId, { type: 'bytes' }),
        nativeToScVal(resultHash, { type: 'bytes' }),
        xdr.ScVal.scvVec(signers),
      ),
    )
    .setTimeout(30)
    .build();

  const prepared = await server.prepareTransaction(tx);
  aggregatorKeypair.sign(prepared);
  await server.sendTransaction(prepared);
}
```

## Reading the Settlement Result

```ts
// lib/read-result.ts
import { Contract, rpc, xdr } from '@stellar/stellar-sdk';

export async function getJobResult(
  jobId: Buffer,
): Promise<{ resultHash: string; settledAt: number } | null> {
  const server = new rpc.Server(process.env.NEXT_PUBLIC_RPC_URL!);
  const contract = new Contract(process.env.NEXT_PUBLIC_SETTLEMENT_CONTRACT!);

  const key = xdr.ScVal.scvBytes(jobId);
  const response = await server.getContractData(
    contract.contractId(),
    key,
    rpc.Durability.Persistent,
  );

  if (!response?.val) return null;

  const map = response.val.value() as xdr.ScMapEntry[];
  // Parse JobResult struct fields
  const resultHash = map.find(e => e.key().value() === 'result')
    ?.val().bytes().toString('hex') ?? '';
  const settledAt = Number(
    map.find(e => e.key().value() === 'settled_at')?.val().u64() ?? 0,
  );

  return { resultHash, settledAt };
}
```

## Operational Considerations

### Replay Protection

The contract rejects a `job_id` that already has a stored result. Assign job IDs as UUIDs or content-hashes of the input — never reuse them.

### Executor Key Rotation

Add an `update_executors` function gated behind the existing threshold of current executors. Require a supermajority (e.g. N-of-M where N > threshold) for the rotation itself to prevent a small coalition from swapping in colluding keys.

### Latency vs Safety

The multi-sig pattern has no dispute window — settlement is immediate once the threshold is met. For high-value settlements, add a time-lock in the contract that delays execution by a configurable period, giving watchtowers a window to dispute via an `override_admin` address.
