# Token Airdrop System Tutorial

An airdrop distributes tokens to a predefined set of eligible addresses. This tutorial builds a Soroban airdrop contract that stores a merkle-style allowlist, lets addresses claim their allocation exactly once, and explains how to batch large distributions off-chain.

---

## Design Overview

| Component | Responsibility |
|-----------|---------------|
| Airdrop contract | Stores allocations, enforces single claim, transfers tokens |
| Token contract | SAC or custom Soroban token holding the airdrop supply |
| Off-chain script | Populates allocations, drives batch initialization |

---

## Data Model

```rust
#![no_std]
use soroban_sdk::{contract, contractimpl, contracttype, token, Address, Env, Symbol};

#[contracttype]
pub enum DataKey {
    Admin,
    Token,
    Allocation(Address), // address → claimable amount
    Claimed(Address),    // address → bool
}
```

---

## Initialization

```rust
#[contract]
pub struct Airdrop;

#[contractimpl]
impl Airdrop {
    pub fn initialize(env: Env, admin: Address, token: Address) {
        assert!(!env.storage().instance().has(&DataKey::Admin), "already initialized");
        env.storage().instance().set(&DataKey::Admin, &admin);
        env.storage().instance().set(&DataKey::Token, &token);
    }
```

## Loading Allocations

The admin loads eligible addresses and amounts before the claim window opens.

```rust
    pub fn set_allocation(env: Env, caller: Address, recipient: Address, amount: i128) {
        caller.require_auth();
        let admin: Address = env.storage().instance().get(&DataKey::Admin).unwrap();
        assert!(caller == admin, "unauthorized");
        assert!(amount > 0, "amount must be positive");
        assert!(
            !env.storage().instance().has(&DataKey::Claimed(recipient.clone())),
            "recipient already claimed"
        );
        env.storage().instance().set(&DataKey::Allocation(recipient), &amount);
    }
```

---

## Claiming

```rust
    pub fn claim(env: Env, recipient: Address) {
        recipient.require_auth();

        assert!(
            !env.storage().instance().get::<_, bool>(&DataKey::Claimed(recipient.clone())).unwrap_or(false),
            "already claimed"
        );

        let amount: i128 = env.storage().instance()
            .get(&DataKey::Allocation(recipient.clone()))
            .expect("not eligible");

        env.storage().instance().set(&DataKey::Claimed(recipient.clone()), &true);

        let token: Address = env.storage().instance().get(&DataKey::Token).unwrap();
        token::Client::new(&env, &token).transfer(
            &env.current_contract_address(),
            &recipient,
            &amount,
        );

        env.events().publish((Symbol::new(&env, "claim"), recipient), amount);
    }
}
```

Marking `Claimed` before transferring prevents re-entrancy from triggering a second transfer.

## Batching Considerations

Soroban has per-transaction instruction limits. Loading 10,000 allocations in a single transaction will exceed them. Instead, batch `set_allocation` calls off-chain:

```ts
import { Contract, SorobanRpc, TransactionBuilder, Networks, BASE_FEE } from "@stellar/stellar-sdk";

const server    = new SorobanRpc.Server("https://soroban-testnet.stellar.org");
const CONTRACT  = "C...";
const BATCH     = 50; // allocations per transaction

async function loadAllocations(
  adminKeypair: Keypair,
  allocations: { address: string; amount: bigint }[]
) {
  for (let i = 0; i < allocations.length; i += BATCH) {
    const batch   = allocations.slice(i, i + BATCH);
    const account = await server.getAccount(adminKeypair.publicKey());
    const contract = new Contract(CONTRACT);

    let builder = new TransactionBuilder(account, {
      fee: BASE_FEE,
      networkPassphrase: Networks.TESTNET,
    });

    for (const { address, amount } of batch) {
      builder = builder.addOperation(
        contract.call("set_allocation", /* admin Address xdr, recipient Address xdr, amount i128 xdr */)
      );
    }

    const tx       = builder.setTimeout(30).build();
    const prepared = await server.prepareTransaction(tx);
    prepared.sign(adminKeypair);
    await server.sendTransaction(prepared);

    console.log(`Loaded allocations ${i + 1}–${Math.min(i + BATCH, allocations.length)}`);
  }
}
```

## Eligibility Snapshot

Compute the eligible set off-chain before loading:

```ts
import { Horizon } from "@stellar/stellar-sdk";

const horizon = new Horizon.Server("https://horizon-testnet.stellar.org");

async function snapshotHolders(assetCode: string, assetIssuer: string, minBalance: string) {
  const eligible: { address: string; amount: bigint }[] = [];
  let page = await horizon.accounts().forAsset(new Asset(assetCode, assetIssuer)).limit(200).call();

  while (page.records.length > 0) {
    for (const account of page.records) {
      const balance = account.balances.find(
        (b: any) => b.asset_code === assetCode && b.asset_issuer === assetIssuer
      );
      if (balance && parseFloat(balance.balance) >= parseFloat(minBalance)) {
        eligible.push({ address: account.account_id, amount: BigInt(1_000_0000) }); // 1 token in stroops
      }
    }
    page = await page.next();
  }
  return eligible;
}
```

## Abuse Prevention

| Risk | Mitigation |
|------|-----------|
| Double claim | `Claimed` flag set atomically before transfer |
| Unauthorized allocation loading | `set_allocation` gated by admin auth |
| Snapshot manipulation | Snapshot at a fixed past ledger sequence before announcing the airdrop |
| Contract drain | Pre-fund contract with exactly the total allocation; admin cannot withdraw mid-airdrop |

---

## Accuracy Notes

- The contract must hold sufficient token balance before any claim is processed; transfer tokens into the contract address after deploying.
- `env.storage().instance()` has a default TTL of ~100 ledgers; extend it or use persistent storage for long claim windows.
- For very large airdrops (100k+ addresses), consider a merkle-proof approach where only the root is stored on-chain and proofs are verified at claim time.
