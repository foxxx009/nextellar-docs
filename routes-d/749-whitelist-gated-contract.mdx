# Whitelist-Gated Contract Tutorial

A whitelist-gated contract restricts function access to a pre-approved set of addresses. This is useful for private mints, early-access features, partner APIs, and any scenario where you need to control who can interact with a contract. This tutorial covers whitelist storage, access-controlled functions, and the governance flow for managing the list.

---

## Design Options

| Storage approach | Lookup cost | Scalability | Best for |
|-----------------|------------|-------------|---------|
| `Map<Address, bool>` in instance | O(1) | ~hundreds | Small, fixed lists |
| `persistent` storage per address | O(1) | Unlimited | Large or dynamic lists |
| Off-chain merkle proof verified on-chain | O(log n) | Unlimited, no per-address storage | Snapshot-based lists |

This tutorial uses persistent storage per address, which scales to any list size.

## Data Model

```rust
#![no_std]
use soroban_sdk::{contract, contractimpl, contracttype, Address, Env, Symbol};

#[contracttype]
pub enum DataKey {
    Admin,
    Whitelisted(Address),
}
```

---

## Initialization

```rust
#[contract]
pub struct WhitelistGated;

#[contractimpl]
impl WhitelistGated {
    pub fn initialize(env: Env, admin: Address) {
        assert!(!env.storage().instance().has(&DataKey::Admin), "already initialized");
        env.storage().instance().set(&DataKey::Admin, &admin);
    }
```

## Managing the Whitelist

```rust
    pub fn add(env: Env, caller: Address, address: Address) {
        caller.require_auth();
        let admin: Address = env.storage().instance().get(&DataKey::Admin).unwrap();
        assert!(caller == admin, "unauthorized");

        env.storage().persistent().set(&DataKey::Whitelisted(address.clone()), &true);

        env.events().publish((Symbol::new(&env, "added"), address), ());
    }

    pub fn remove(env: Env, caller: Address, address: Address) {
        caller.require_auth();
        let admin: Address = env.storage().instance().get(&DataKey::Admin).unwrap();
        assert!(caller == admin, "unauthorized");

        env.storage().persistent().remove(&DataKey::Whitelisted(address.clone()));

        env.events().publish((Symbol::new(&env, "removed"), address), ());
    }

    pub fn is_whitelisted(env: Env, address: Address) -> bool {
        env.storage().persistent()
            .get::<_, bool>(&DataKey::Whitelisted(address))
            .unwrap_or(false)
    }
```

## Gated Function

Any function that should be whitelist-restricted calls the check at the top:

```rust
    pub fn exclusive_action(env: Env, caller: Address) -> i128 {
        caller.require_auth();

        assert!(
            env.storage().persistent()
                .get::<_, bool>(&DataKey::Whitelisted(caller.clone()))
                .unwrap_or(false),
            "not whitelisted"
        );

        // Protected logic here
        env.events().publish((Symbol::new(&env, "action"), caller), ());
        42_i128
    }
}
```

## Governance Flows

### Adding addresses in bulk (off-chain script)

```ts
import { Contract, SorobanRpc, TransactionBuilder, Networks, BASE_FEE } from "@stellar/stellar-sdk";

const server   = new SorobanRpc.Server("https://soroban-testnet.stellar.org");
const CONTRACT = "C...";
const BATCH    = 20; // addresses per transaction

async function bulkAdd(adminKeypair: Keypair, addresses: string[]) {
  for (let i = 0; i < addresses.length; i += BATCH) {
    const batch    = addresses.slice(i, i + BATCH);
    const account  = await server.getAccount(adminKeypair.publicKey());
    const contract = new Contract(CONTRACT);

    let builder = new TransactionBuilder(account, {
      fee: BASE_FEE,
      networkPassphrase: Networks.TESTNET,
    });

    for (const addr of batch) {
      builder = builder.addOperation(
        contract.call("add", /* admin Address xdr, addr Address xdr */)
      );
    }

    const tx       = builder.setTimeout(30).build();
    const prepared = await server.prepareTransaction(tx);
    prepared.sign(adminKeypair);
    await server.sendTransaction(prepared);
    console.log(`Added ${i + batch.length} of ${addresses.length}`);
  }
}
```

### Delegating admin to a multi-sig

Replace the single admin address at initialization with a multi-sig account. All `add` and `remove` calls then require the configured threshold of signatures:

```ts
// Initialize with a multi-sig public key
await contract.call("initialize", /* multiSigPublicKey as Address xdr */);

// add() calls must come from a tx signed by the multi-sig's required signers
```

## Governance Flows Summary

| Action | Who | How |
|--------|-----|-----|
| Add an address | Admin | `add(admin, address)` |
| Remove an address | Admin | `remove(admin, address)` |
| Check access | Anyone | `is_whitelisted(address)` returns bool |
| Bulk add | Admin | Off-chain script batching `add` operations |
| Transfer admin | Current admin | Add a `set_admin` function |
| Public whitelist (open access) | — | Remove gating check from the function |

## Accuracy Notes

- `env.storage().persistent()` entries have independent TTLs; extend them with `env.storage().persistent().extend_ttl(key, ...)` if your whitelist must survive past the default ~100-ledger window.
- Persistent storage costs more XLM in rent than instance storage; for lists under ~100 entries, instance storage with a `Map<Address, bool>` is cheaper.
- Emitting `added` and `removed` events lets an indexer maintain a queryable off-chain copy of the whitelist without scanning contract state.
- For snapshot-based allowlists (e.g. "all holders at block N"), a merkle root approach avoids storing per-address entries and is more gas-efficient at scale.
