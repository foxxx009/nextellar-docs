# Soroban Contract Migration Strategies

Soroban contracts evolve. You might fix a bug, add a function, or change a storage layout. This guide compares the two main migration strategies, explains data migration steps, and provides a worked example of each.

---

## Strategy Comparison

| | In-place Wasm upgrade | New deployment + swap |
|-|----------------------|-----------------------|
| **Contract ID changes?** | No — same ID | Yes — new ID |
| **Storage preserved?** | Yes — same contract storage | No — must migrate explicitly |
| **Client code update needed?** | No (same ID) | Yes (new ID) |
| **Breaking storage changes safe?** | Only if migration logic handles them | Yes — fresh storage |
| **Rollback** | Re-upgrade to old Wasm | Keep old contract running |
| **Best for** | Bug fixes, new functions, compatible layout changes | Major redesigns, breaking storage changes |

---

## In-Place Wasm Upgrade

Soroban's `update_current_contract_wasm` host function replaces the bytecode while preserving storage and the contract ID.

### Adding an upgrade function

```rust
#![no_std]
use soroban_sdk::{contract, contractimpl, Address, BytesN, Env};

#[contract]
pub struct MyContract;

#[contractimpl]
impl MyContract {
    pub fn upgrade(env: Env, caller: Address, new_wasm_hash: BytesN<32>) {
        caller.require_auth();
        let admin: Address = env.storage().instance().get(&"admin").unwrap();
        assert!(caller == admin, "unauthorized");
        env.deployer().update_current_contract_wasm(new_wasm_hash);
    }

    // ... rest of contract functions
}
```

### Uploading and triggering the upgrade

```ts
import { SorobanRpc, TransactionBuilder, Operation, Networks, BASE_FEE } from "@stellar/stellar-sdk";
import fs from "fs";

const server = new SorobanRpc.Server("https://soroban-testnet.stellar.org");

async function uploadWasm(adminKeypair: Keypair, wasmPath: string): Promise<string> {
  const wasm    = fs.readFileSync(wasmPath);
  const account = await server.getAccount(adminKeypair.publicKey());
  const tx = new TransactionBuilder(account, { fee: BASE_FEE, networkPassphrase: Networks.TESTNET })
    .addOperation(Operation.uploadContractWasm({ wasm }))
    .setTimeout(30)
    .build();

  const prepared = await server.prepareTransaction(tx);
  prepared.sign(adminKeypair);
  const result = await server.sendTransaction(prepared);
  // Extract Wasm hash from result returnValue
  return result.returnValue?.toXDR("base64") ?? "";
}

async function triggerUpgrade(adminKeypair: Keypair, contractId: string, wasmHash: string) {
  const account  = await server.getAccount(adminKeypair.publicKey());
  const contract = new Contract(contractId);
  const tx = new TransactionBuilder(account, { fee: BASE_FEE, networkPassphrase: Networks.TESTNET })
    .addOperation(contract.call("upgrade", /* admin Address xdr, wasmHash BytesN<32> xdr */))
    .setTimeout(30)
    .build();

  const prepared = await server.prepareTransaction(tx);
  prepared.sign(adminKeypair);
  return server.sendTransaction(prepared);
}
```

## Data Migration Steps (In-Place)

When the new Wasm version changes a storage key's type or layout, add a `migrate` function that transforms old data into the new format. Run it once after upgrading.

```rust
// v1 stored Counter as u32; v2 stores it as i128
pub fn migrate_counter(env: Env, caller: Address) {
    caller.require_auth();
    let admin: Address = env.storage().instance().get(&"admin").unwrap();
    assert!(caller == admin, "unauthorized");

    if let Some(old_val) = env.storage().instance().get::<_, u32>(&"counter_v1") {
        let new_val: i128 = old_val as i128;
        env.storage().instance().set(&"counter_v2", &new_val);
        env.storage().instance().remove(&"counter_v1");
    }
}
```

**Rules for safe in-place migration:**
- Never re-use an existing key name with a different type — deserialization panics.
- Write new keys, then remove old ones.
- Run the migration in a dedicated transaction immediately after the upgrade transaction.
- Test on a testnet fork with production-like storage before mainnet.

## New Deployment + Swap

For breaking changes, deploy a fresh contract and migrate state off-chain (or via a migration script contract).

```ts
async function deployNewContract(adminKeypair: Keypair, wasmPath: string): Promise<string> {
  const wasmHash  = await uploadWasm(adminKeypair, wasmPath);
  const account   = await server.getAccount(adminKeypair.publicKey());

  // Generate a new contract salt so the address differs from the old one
  const salt = crypto.randomBytes(32);
  const tx = new TransactionBuilder(account, { fee: BASE_FEE, networkPassphrase: Networks.TESTNET })
    .addOperation(
      Operation.invokeHostFunction({
        func: xdr.HostFunction.hostFunctionTypeCreateContract(
          new xdr.CreateContractArgs({
            contractIdPreimage: xdr.ContractIdPreimage.contractIdPreimageFromAddress(
              new xdr.ContractIdPreimageFromAddress({
                address: xdr.ScAddress.scAddressTypeAccount(
                  xdr.PublicKey.publicKeyTypeEd25519(keypairToRawEd25519(adminKeypair))
                ),
                salt: Buffer.from(salt),
              })
            ),
            executable: xdr.ContractExecutable.contractExecutableWasm(
              Buffer.from(wasmHash, "hex")
            ),
          })
        ),
        auth: [],
      })
    )
    .setTimeout(30)
    .build();

  const prepared = await server.prepareTransaction(tx);
  prepared.sign(adminKeypair);
  const result = await server.sendTransaction(prepared);
  return result.returnValue?.address().contractId().toString("hex") ?? "";
}
```

After deploying, update your dApp's `CONTRACT_ID` environment variable and re-deploy the frontend.

## Worked Example: Adding a New Field

**Scenario**: v1 stores `{ owner: Address, amount: i128 }`. v2 adds `locked: bool`.

1. Write v2 contract with the new field defaulting to `false` on first access.
2. Upload v2 Wasm, get hash.
3. Call `upgrade(admin, new_wasm_hash)`.
4. Call `migrate()` to backfill `locked: false` for all existing entries (if needed).
5. Existing storage is intact — `owner` and `amount` keys are unchanged.

## Accuracy Notes

- `update_current_contract_wasm` takes effect on the **next invocation** after the upgrade ledger closes.
- The old Wasm bytecode is no longer executable after an in-place upgrade; keep a copy off-chain if rollback is needed.
- Always test upgrades on testnet with a snapshot of mainnet storage before touching mainnet.
- Persistent storage TTL is independent of the contract's instance TTL; check and extend both after deploying.
