# Stellar Consortia Setup Guide

A Stellar consortium is a group of independent organizations that operate a shared Stellar account (or set of accounts) under multi-party rules. Common use cases include inter-bank settlement networks, supply-chain finance rails, and tokenized asset clearing systems. This guide walks through account setup, governance mechanics, key management, and day-to-day operations.

---

## What a Consortium Needs

| Requirement | Stellar primitive |
|-------------|-------------------|
| Multiple parties must approve transactions | Multi-signature thresholds |
| Any single member can propose but not unilaterally execute | Low/medium/high weight split |
| Membership can change | `SetOptions` to add/remove signers |
| Immutable record of decisions | On-chain transactions |
| Shared assets / reserve | Consortium master account |

## Account Structure

A typical three-member consortium uses a **master account** owned by no single party:

```
Consortium Master Account
  Signers:
    MemberA (weight 1)
    MemberB (weight 1)
    MemberC (weight 1)
  Thresholds:
    low:    1  (any signer can query)
    medium: 2  (payments, offers require 2-of-3)
    high:   3  (signer changes require all 3)
```

```ts
import { Keypair, TransactionBuilder, Operation, Networks, BASE_FEE } from "@stellar/stellar-sdk";
import Horizon from "@stellar/stellar-sdk";

const server = new Horizon.Server("https://horizon-testnet.stellar.org");

async function setupConsortiumAccount(
  masterKeypair: Keypair,
  memberPublicKeys: string[]
) {
  const account = await server.loadAccount(masterKeypair.publicKey());

  let builder = new TransactionBuilder(account, {
    fee: BASE_FEE,
    networkPassphrase: Networks.TESTNET,
  });

  // Set thresholds: medium = 2-of-3 for payments, high = 3-of-3 for governance
  builder = builder.addOperation(
    Operation.setOptions({
      lowThreshold:    1,
      medThreshold:    2,
      highThreshold:   3,
      masterWeight:    0, // master key alone cannot sign anything
    })
  );

  // Add each member as a signer with weight 1
  for (const pubKey of memberPublicKeys) {
    builder = builder.addOperation(
      Operation.setOptions({
        signer: { ed25519PublicKey: pubKey, weight: 1 },
      })
    );
  }

  const tx = builder.setTimeout(60).build();
  tx.sign(masterKeypair);
  return server.submitTransaction(tx);
}
```

Setting `masterWeight: 0` ensures the key used to create the account can never sign on its own, preventing a founding member from unilaterally controlling funds.

## Proposing and Collecting Signatures Off-Chain

Stellar transactions require all signatures before submission. Use a simple coordination flow:

```ts
import { TransactionBuilder, Transaction, Networks } from "@stellar/stellar-sdk";

// Member A proposes a payment and signs it
async function proposePayment(
  proposerKeypair: Keypair,
  consortiumPublicKey: string,
  destination: string,
  amount: string,
  server: Horizon.Server
): Promise<string> {
  const account = await server.loadAccount(consortiumPublicKey);
  const tx = new TransactionBuilder(account, {
    fee: BASE_FEE,
    networkPassphrase: Networks.TESTNET,
  })
    .addOperation(Operation.payment({ destination, asset: Asset.native(), amount }))
    .setTimeout(300) // 5-minute signing window
    .build();

  tx.sign(proposerKeypair);
  return tx.toXDR(); // Share XDR with other members for co-signing
}

// Member B adds their signature and returns the updated XDR
function cosign(txXdr: string, signerKeypair: Keypair): string {
  const tx = new Transaction(txXdr, Networks.TESTNET);
  tx.sign(signerKeypair);
  return tx.toXDR();
}

// After 2 signatures collected, submit
async function submit(txXdr: string, server: Horizon.Server) {
  const tx = new Transaction(txXdr, Networks.TESTNET);
  return server.submitTransaction(tx);
}
```

In production, share the XDR over an authenticated API endpoint or encrypted channel between members.

## Membership Changes

Adding a new member requires all three current signers (`highThreshold = 3`):

```ts
async function addMember(
  consortiumPublicKey: string,
  newMemberPublicKey: string,
  allSignerKeypairs: Keypair[],
  server: Horizon.Server
) {
  const account = await server.loadAccount(consortiumPublicKey);
  const tx = new TransactionBuilder(account, {
    fee: BASE_FEE,
    networkPassphrase: Networks.TESTNET,
  })
    .addOperation(
      Operation.setOptions({
        signer: { ed25519PublicKey: newMemberPublicKey, weight: 1 },
        // Raise thresholds to reflect 4-of-4 governance after adding new member
        medThreshold: 3,
        highThreshold: 4,
      })
    )
    .setTimeout(300)
    .build();

  for (const kp of allSignerKeypairs) {
    tx.sign(kp);
  }
  return server.submitTransaction(tx);
}
```

Removing a member follows the same pattern but sets `weight: 0` for the departing signer.

## Key Management Recommendations

| Practice | Why |
|----------|-----|
| Each member holds their signing key in an HSM or hardware wallet | Private key never touches application memory |
| Store XDR proposals in an immutable log (database with audit trail) | Non-repudiation of who proposed what |
| Rotate signing keys annually | Limit blast radius of key compromise |
| Use `timeBounds` on every transaction | Proposals expire if quorum is not reached |
| Run a separate `lowThreshold` key for read operations | Reduces high-value key usage frequency |

## On-Chain Governance Notes

- Stellar's multi-sig is synchronous — you collect signatures off-chain, then submit once the threshold is met.
- All signers' weights and thresholds are visible on-chain via `GET /accounts/{id}`; the governance rules are auditable by anyone.
- Consider holding a small XLM reserve in each member's account to cover their `SetOptions` and other transaction fees, rather than draining the consortium master account.
- Testnet accounts can be funded via Friendbot (`https://friendbot.stellar.org/?addr=PUBLIC_KEY`).
