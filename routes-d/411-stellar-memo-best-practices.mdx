# Stellar Memo Best Practices

A memo is an optional field on Stellar transactions that travels with the payment on-chain. It's public, permanent, and limited in size. Used well, it ties payments to off-chain records. Used poorly, it leaks data or breaks integrations.

---

## Memo Types

Stellar supports four memo types plus "none":

| Type            | Max Size | Format                               | Use When                                                           |
| --------------- | -------- | ------------------------------------ | ------------------------------------------------------------------ |
| **MEMO_TEXT**   | 28 bytes | Human-readable string                | Exchanges require a deposit memo, or you need a short label        |
| **MEMO_ID**     | 8 bytes  | Unsigned 64-bit integer              | You need a numeric reference (order ID, invoice number)            |
| **MEMO_HASH**   | 32 bytes | Arbitrary byte array (hex-encoded)   | You need a longer reference that doesn't need to be human-readable |
| **MEMO_RETURN** | 32 bytes | Hash of the original transaction XDR | You're returning or referencing a specific prior transaction       |
| **None**        | —        | No memo attached                     | Self-custodied wallets, internal transfers, Soroban calls          |

Most dApps use `MEMO_TEXT` or no memo. The others exist for specific use cases.

---

## Size Constraints

| Type        | Limit    | Encoding       | Overhead                     |
| ----------- | -------- | -------------- | ---------------------------- |
| MEMO_TEXT   | 28 bytes | UTF-8          | ~30–60 bytes per transaction |
| MEMO_ID     | 8 bytes  | XDR int64      | ~20 bytes per transaction    |
| MEMO_HASH   | 32 bytes | Hex (64 chars) | ~40 bytes per transaction    |
| MEMO_RETURN | 32 bytes | Hex (64 chars) | ~40 bytes per transaction    |

**Key details:**

- Text memos are UTF-8 encoded. Multi-byte characters (emoji, CJK) consume more than one byte per visual character. A 28-character string with multi-byte characters will be rejected.
- The SDK validates text memo length at build time. If your memo exceeds 28 bytes, the transaction build fails before submission.
- Hash and return memos are always 32 bytes regardless of content.

---

## Choosing a Memo Type

```
Do you need a memo?
├── No  → omit it (none)
├── Exchange or anchor requires it → MEMO_TEXT (short label, ≤28 bytes)
├── Numeric reference (order/invoice ID) → MEMO_ID (≤2^64 - 1)
├── Longer reference (hash, fingerprint) → MEMO_HASH (≤32 bytes)
└── Referencing a specific prior transaction → MEMO_RETURN
```

### Decision Rules

1. **Omit when possible.** Memos add bytes and are permanent. If the recipient doesn't need it, leave it out.
2. **Use MEMO_TEXT for exchanges.** Most exchanges and anchors expect a text memo for deposit routing.
3. **Use MEMO_HASH for internal references.** If you need to link a payment to an order but the order ID exceeds 28 bytes, hash it and store the hash in your database.
4. **Never put PII in a memo.** Memos are public and permanent on the ledger. Names, emails, and addresses belong off-chain.

## Example: Text Memo with useStellarPayment

```tsx
'use client';

import { useState } from 'react';
import { useStellarPayment } from '@/hooks/useStellarPayment';

export function PayInvoice() {
  const { buildPaymentXDR, loading, error } = useStellarPayment();
  const [status, setStatus] = useState('');

  const pay = async () => {
    const xdr = await buildPaymentXDR({
      from: 'GABC123...',
      to: 'GDEF456...',
      amount: '25.00',
      asset: 'XLM',
      memo: 'Invoice #4821', // 14 bytes — under the 28-byte limit
    });
    setStatus('XDR built — sign with wallet');
  };

  return (
    <div>
      <button onClick={pay} disabled={loading}>
        {loading ? 'Building...' : 'Pay Invoice'}
      </button>
      {status && <p>{status}</p>}
      {error && <p>Error: {error}</p>}
    </div>
  );
}
```

## Example: Hash Memo for Order Linking

When the order ID exceeds 28 bytes, hash it before attaching:

```ts
import crypto from 'crypto';

function orderMemo(orderId: string): string {
  return crypto.createHash('sha256').update(orderId).digest('hex').slice(0, 28);
}

// "ord_2026_abc123def456ghi789jkl012" → 32 chars, exceeds text limit
// Hashed → 28-char hex string, fits MEMO_TEXT
```

Alternatively, use `MEMO_HASH` directly with the full 32-byte digest:

```ts
import { Memo } from '@stellar/stellar-sdk';

const hash = crypto.createHash('sha256').update(orderId).digest();
const memo = Memo.hash(hash);
```

Store the hash in your database and match incoming payments by memo value.

## Common Pitfalls

| Pitfall                                    | Cause                                      | Fix                                                   |
| ------------------------------------------ | ------------------------------------------ | ----------------------------------------------------- |
| Transaction rejected with `memos too long` | Text memo exceeds 28 bytes                 | Truncate, hash, or switch to `MEMO_HASH`              |
| Multi-byte characters rejected             | UTF-8 emoji or CJK count as multiple bytes | Use ASCII or check byte length, not character length  |
| Payment received but not matched           | Wrong memo type or encoding                | Ensure sender and receiver agree on type and encoding |
| PII exposed on ledger                      | Name or email in text memo                 | Remove PII — use an internal reference ID instead     |
| Exchange deposit lost                      | Missing or wrong memo                      | Always include the exact memo the exchange specifies  |
