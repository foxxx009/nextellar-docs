# Background Job Processing for Stellar dApps

Stellar transactions must be signed and submitted within a 30-second default time-out window. Long-running work — sending batch payments, syncing ledger events, retrying failed submissions — must happen outside the request/response cycle. This guide covers the queue and retry patterns you need to build reliable background job pipelines against Stellar.

---

## Why Background Jobs?

| Scenario | Why not synchronous? |
|---|---|
| Sending XLM to 500 recipients | Sequence-number exhaustion if all submitted at once |
| Polling Horizon for events | Blocks the web server; needs its own loop |
| Retrying failed transactions | Requires exponential back-off, not a user-facing concern |
| Resubmitting fee-bumped transactions | Needs state across multiple HTTP requests |

---

## Queue Architecture

```
┌──────────────┐    enqueue     ┌───────────────┐    process    ┌─────────────────┐
│  API Server  │ ─────────────► │  Job Queue    │ ────────────► │  Worker Process │
│  (Next.js)   │                │  (BullMQ /    │               │  (Stellar SDK)  │
└──────────────┘                │   Redis)      │               └────────┬────────┘
                                └───────────────┘                        │
                                        ▲                                │ submit tx
                                        │  retry on failure              ▼
                                        └──────────────────── Horizon / RPC
```

A **producer** (your API route) pushes job descriptors into the queue. A **consumer** (a separate worker process) pulls jobs, builds and submits Stellar transactions, and handles failures — all without blocking user requests.

## Retry Strategy

Stellar transactions fail for two distinct reasons that need different retry behaviour:

| Failure type | Error code | Action |
|---|---|---|
| Insufficient fee (surge pricing) | `tx_insufficient_fee` | Retry with higher fee |
| Bad sequence number | `tx_bad_seq` | Re-fetch account, rebuild, retry |
| Network timeout | `ECONNRESET` / 504 | Retry with back-off |
| Transaction already submitted | `tx_already_ingested` | Mark complete — do not retry |
| Permanent error (bad auth, etc.) | `tx_bad_auth` | Dead-letter — do not retry |

```ts
// workers/payment.worker.ts
import { Worker, Job } from 'bullmq';
import {
  Horizon,
  Keypair,
  Networks,
  TransactionBuilder,
  BASE_FEE,
  Asset,
  Operation,
  Memo,
} from '@stellar/stellar-sdk';
import { connection } from '../lib/queue';

interface PaymentJob {
  destination: string;
  assetCode: string;
  assetIssuer: string | 'native';
  amount: string;
  memo?: string;
}

const server = new Horizon.Server(process.env.HORIZON_URL!);
const signerKeypair = Keypair.fromSecret(process.env.SIGNER_SECRET!);

const worker = new Worker<PaymentJob>(
  'stellar-payments',
  async (job: Job<PaymentJob>) => {
    const { destination, assetCode, assetIssuer, amount, memo } = job.data;

    const account = await server.loadAccount(signerKeypair.publicKey());
    const asset =
      assetIssuer === 'native'
        ? Asset.native()
        : new Asset(assetCode, assetIssuer);

    const feeStats = await server.feeStats();
    const fee = String(
      Math.max(
        Number(BASE_FEE),
        Number(feeStats.fee_charged.p90) * 2, // headroom above p90
      ),
    );

    const builder = new TransactionBuilder(account, {
      fee,
      networkPassphrase: Networks.MAINNET,
    }).addOperation(
      Operation.payment({ destination, asset, amount }),
    );

    if (memo) builder.addMemo(Memo.text(memo));

    const tx = builder.setTimeout(30).build();
    tx.sign(signerKeypair);

    const result = await server.submitTransaction(tx);
    return { hash: result.hash };
  },
  {
    connection,
    attempts: 5,
    backoff: {
      type: 'exponential',
      delay: 2000, // 2s, 4s, 8s, 16s, 32s
    },
  },
);

worker.on('failed', (job, err) => {
  // Permanent errors should not be retried
  if (isPermanentError(err)) {
    job?.discard(); // Move to failed immediately, skip remaining attempts
  }
  console.error(`Job ${job?.id} failed:`, err.message);
});

function isPermanentError(err: unknown): boolean {
  if (err instanceof Error) {
    const code = (err as any)?.response?.data?.extras?.result_codes?.transaction;
    return ['tx_bad_auth', 'tx_no_source_account', 'tx_not_supported'].includes(code ?? '');
  }
  return false;
}
```

## Idempotency

A job may run more than once — the worker could crash after submitting but before recording success, causing a retry. Without idempotency, the same payment fires twice.

### Strategy 1 — Horizon's `already_ingested` check

Stellar rejects a transaction with the same hash twice (`tx_already_ingested`). Build the transaction deterministically from a stable `sequence_number` so the same logical operation always produces the same hash. If the retry gets `tx_already_ingested`, treat it as success.

```ts
// Check before resubmitting
if (horizonError?.response?.data?.extras?.result_codes?.transaction === 'tx_already_ingested') {
  return { hash: 'already_settled', idempotent: true };
}
```

### Strategy 2 — Idempotency key in the queue

Assign a stable `jobId` at enqueue time (e.g. `sha256(user_id + payment_id)`). BullMQ deduplicates jobs with the same ID within a configurable window:

```ts
await paymentQueue.add(
  'send-payment',
  jobData,
  {
    jobId: `payment:${userId}:${paymentId}`, // stable key
    removeOnComplete: { age: 86400 }, // keep 24 h for dedup
  },
);
```

## Enqueuing from an API Route

```ts
// app/api/payments/route.ts
import { NextRequest, NextResponse } from 'next/server';
import { paymentQueue } from '@/lib/queue';
import { createHash } from 'crypto';

export async function POST(req: NextRequest) {
  const body = await req.json();
  const { userId, destination, amount, assetCode, assetIssuer, memo } = body;

  const paymentId = createHash('sha256')
    .update(`${userId}:${destination}:${amount}:${assetCode}`)
    .digest('hex')
    .slice(0, 16);

  await paymentQueue.add(
    'send-payment',
    { destination, assetCode, assetIssuer: assetIssuer ?? 'native', amount, memo },
    { jobId: `payment:${userId}:${paymentId}` },
  );

  return NextResponse.json({ queued: true, paymentId });
}
```

## Monitoring Job Status

```ts
// app/api/payments/[paymentId]/route.ts
import { paymentQueue } from '@/lib/queue';
import { NextRequest, NextResponse } from 'next/server';

export async function GET(
  req: NextRequest,
  { params }: { params: { paymentId: string } },
) {
  const job = await paymentQueue.getJob(`payment:${params.paymentId}`);
  if (!job) return NextResponse.json({ status: 'not_found' }, { status: 404 });

  const state = await job.getState();
  return NextResponse.json({
    status: state,
    attempts: job.attemptsMade,
    result: job.returnvalue ?? null,
    failReason: job.failedReason ?? null,
  });
}
```

## Operational Considerations

### Sequence Number Contention

If multiple workers process payments from the **same source account** concurrently, they will collide on sequence numbers. Solve by:
- **Single worker**: run only one worker instance per source account.
- **Channel accounts**: maintain a pool of funded channel accounts; each worker claims one exclusively.
- **Batch-in-one-transaction**: collect jobs into a single multi-operation transaction (up to 100 ops).

### Dead-Letter Queue

BullMQ moves jobs that exhaust all attempts to the "failed" set. Poll this regularly and alert or page on any entries — a stuck dead-letter queue is usually a sign of a key rotation, fee spike, or Horizon outage.

### Graceful Shutdown

```ts
process.on('SIGTERM', async () => {
  await worker.close(); // Finish in-flight job before exiting
  process.exit(0);
});
```
